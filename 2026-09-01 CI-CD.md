# Clase 2026-09-01: CI/CD

## 1. ¿Qué es CI/CD?

**CI/CD** son las siglas de **Integración Continua** (*Continuous Integration*) y **Despliegue Continuo** (*Continuous Deployment/Delivery*). Es un concepto general que aplica a cualquier tipo de software, **no solo a aplicaciones que corren en Kubernetes**.

Por detrás, la idea es puramente DevOps: acompañar el ciclo de vida del desarrollo haciendo despliegues más seguidos, de forma más integrada y automatizada, dejando atrás los despliegues hechos a mano.

### 1.1 De dónde venimos

Hasta ahora, en este curso, todos los despliegues los hicimos **a mano**:

- Con contenedores redujimos el problema del *empaquetado* de la aplicación (la sección [2 de la clase de Docker y Kubernetes](2026-08-11%20Docker%20y%20Fundamentos%20de%20Kubernetes.md#2-app-de-ejemplo-notes-api)), pero eso no automatizó el despliegue en sí.
- Con el objeto `Deployment` (sección [3.6](2026-08-11%20Docker%20y%20Fundamentos%20de%20Kubernetes.md#36-deployment)), cuando levantamos 1, 2 o 3 Pods lo seguimos haciendo a mano, corriendo `kubectl apply` nosotros mismos.
- Cuando actualizamos la imagen de una app (por ejemplo con `kubectl set image`, como en la actividad de rolling update), también lo disparamos manualmente.

CI/CD es la automatización de todo ese proceso: que actualizar la imagen y desplegarla deje de ser un paso manual y pase a dispararse solo, de forma repetible.

## 2. El problema que resuelve

Sin CI/CD, aparecen tres problemas recurrentes:

- **Construcción repetitiva**: cada persona del equipo termina construyendo la imagen "a su manera", repitiendo pasos manuales que son propensos a error.
- **Configuración inconsistente**: sin un proceso único y automatizado, es fácil que el ambiente de testing termine configurado distinto al de producción.
- **Falta de trazabilidad**: sin un pipeline que registre qué se construyó, cuándo y a partir de qué commit, es difícil saber qué código está corriendo realmente en cada ambiente.

## 3. Integración continua (CI)

La integración continua cubre todo lo que pasa **antes** del despliegue: validar que el código nuevo es correcto y empaquetarlo de forma reproducible. Sus etapas típicas son:

- **Pruebas unitarias automáticas**: correr los tests del proyecto en cada cambio, sin intervención humana (herramientas típicas: `pytest` para Python, `jest` para JS, etc., corridas dentro del pipeline).
- **Construcción de la imagen del contenedor**: tomar el código ya validado y construir la imagen Docker a partir de él (el `docker build` que veníamos haciendo a mano).
- **Empaquetado e inmutabilidad**: la imagen resultante queda con un tag específico y **no se vuelve a modificar**. Si hay un cambio, se construye una imagen *nueva* con un tag *nuevo* — nunca se pisa una imagen ya publicada.

## 4. Despliegue continuo (CD)

El despliegue continuo toma esa imagen ya construida y validada, y la lleva al ambiente correspondiente. Sus etapas típicas son:

- **Actualización del estado deseado**: en Kubernetes, esto es literalmente actualizar el `Deployment` para que apunte a la nueva imagen (equivalente automatizado de nuestro `kubectl set image`).
- **Estrategias de despliegue**: cómo se hace la transición de la versión vieja a la nueva sin causar downtime — por ejemplo, *rolling update* (actividad [actividad-rolling-update](actividad-rolling-update)) o *blue-green* (actividad [actividad-blue-green](actividad-blue-green)).
- **Monitoreo y resiliencia**: una vez desplegada la nueva versión, seguir observando que el sistema esté sano (probes, métricas, logs) para poder reaccionar — incluso revertir — si algo sale mal.

## 5. Las tres fases genéricas de un pipeline

Más allá del detalle de cada etapa, un pipeline de CI/CD se puede pensar en tres fases genéricas:

1. **Git commit y push**: cuando se hace push (o merge) a la rama que dispara el pipeline (por ejemplo `main` o `develop`), arranca automáticamente todo el flujo de integración continua.
2. **Run tests y validación**: se corren las pruebas unitarias y cualquier otra validación del código.
3. **Docker build y push**: se construye la imagen del contenedor y se publica en un registro (Docker Hub, GHCR, etc.) para que quede disponible para el despliegue.

La idea central: **un push a `main` dispara todo esto automáticamente**, sin que nadie tenga que correr los comandos a mano.

## 6. Pipelines como código

Los pipelines se definen como **código declarativo dentro del propio repositorio** (por ejemplo, un archivo YAML en `.github/workflows/`). Esto tiene una consecuencia importante: el pipeline se versiona junto con el código, se puede revisar en un pull request, y queda registrado en el historial de git como cualquier otro cambio.

Una distinción importante que se puede modelar así: el despliegue automatizado a **testing** puede ser distinto (más permisivo, más frecuente) que el despliegue a **producción** (más controlado, quizás con un paso manual de aprobación).

Estructura típica de un archivo de pipeline:

- Un **nombre** (`name`) para identificar el pipeline.
- Un **gatillo** (`on`), por ejemplo un push a la rama `main`.
- Uno o más **jobs**, y dentro de cada uno, una lista de **steps** (pasos) que se ejecutan en orden: por ejemplo, *checkout* del código, `docker build`, `kubectl set image` en el deployment.

## 7. Ejemplo simple y genérico (GitHub Actions)

```yaml
name: build-and-deploy

# Gatillo: se dispara automáticamente en cada push a main
on:
  push:
    branches: [main]

jobs:
  build-and-deploy:
    runs-on: ubuntu-latest
    steps:
      # 1. Traer el código del repo al runner del pipeline
      - name: Checkout code
        uses: actions/checkout@v4

      # 2. Correr las pruebas unitarias (fase de CI)
      - name: Run tests
        run: pytest

      # 3. Construir la imagen con un tag único e inmutable
      #    (por ejemplo, el SHA del commit — nunca "latest")
      - name: Docker build
        run: docker build -t mi-app:${{ github.sha }} .

      # 4. Publicar la imagen en el registro
      - name: Docker push
        run: docker push mi-app:${{ github.sha }}

      # 5. Actualizar el Deployment para que use la nueva imagen (fase de CD)
      - name: Deploy
        run: kubectl set image deployment/mi-app mi-app=mi-app:${{ github.sha }}
```

Esto es un ejemplo genérico para fijar la idea general — la implementación real depende del proveedor de CI (GitHub Actions, GitLab CI, Jenkins, etc.) y de cómo el runner llega hasta el cluster de destino.

## 8. Tags de imagen: nunca `latest` en producción

Un detalle clave de la fase de empaquetado (sección 3): **en producción no se usa el tag `latest`**. `latest` es mutable y ambiguo — no permite saber con certeza qué código hay corriendo ni volver atrás de forma confiable.

En cambio, la práctica habitual es:

- Cada build en **dev/testing** genera una imagen con un tag **único e inmutable** (por ejemplo, el hash del commit o un número de build).
- Esa misma imagen se prueba en los distintos ambientes (dev, testing) **sin reconstruirla** — se usa una única vez y se promueve tal cual.
- Para el despliegue a **producción**, se elige puntualmente, de entre todas las imágenes ya construidas y probadas en dev/testing, **la que quedó validada** — y se la promueve a prod usando ese mismo tag.

Esto garantiza que lo que se prueba en testing es *exactamente* el mismo artefacto (imagen) que termina corriendo en producción, y no una reconstrucción que podría diferir.

## 9. Resumen

1. CI/CD automatiza lo que hasta ahora veníamos haciendo a mano: construir la imagen y desplegarla.
2. **CI** (integración continua) = tests automáticos + build de la imagen + empaquetado inmutable.
3. **CD** (despliegue continuo) = actualizar el estado deseado en el ambiente de destino, con una estrategia de despliegue (rolling update, blue-green) y monitoreo posterior.
4. Un pipeline típico tiene tres fases: push a git → tests/validación → build y push de la imagen.
5. El pipeline se define como código declarativo (YAML) dentro del propio repo, con un nombre, un gatillo (`on push`) y jobs compuestos de steps.
6. En producción nunca se usa el tag `latest`: se promueve una imagen inmutable ya validada en ambientes previos.
